## Goal

Reproduce and fix the error that occurs when the user selects and starts
Rootless Linux on the current main branch.

On a supported ARM64 Android target, the completed flow must:

1. require no root, ADB grant, AVF permission, or user-supplied executable;
2. provision the pinned Debian rootfs safely when it is not installed;
3. resolve an immutable APK-packaged PRoot executable and loader;
4. start a Rootless Debian PTY session through the existing unified session
   architecture;
5. show a usable shell in the terminal UI;
6. preserve the session across ordinary UI detach/recreation;
7. recover cleanly from a failed or interrupted first installation.

Do not merely improve the error message. Find and fix the first failing cause,
then validate the complete Rootless startup path far enough to expose and fix
any next blocker.

## Repository evidence to verify

The command author observed the following on commit
beac173b60918266a9a9b70bd8aa3fcc233369b2:

1. ApkNativeExecutableLoader resolves the allow-listed names proot and
   proot-loader as libproot.so and libproot-loader.so below
   ApplicationInfo.nativeLibraryDir.
2. RootlessDebianBackend.prepare requires both files before start.
3. A recursive tree inspection found libtermux.so payloads but no
   libproot.so or libproot-loader.so payload for any ABI.
4. The documentation nevertheless says PRoot and its loader are packaged in
   the APK.
5. RootlessBootstrapper also depends on a pinned GitHub release URL, SHA-256,
   archive root name, link layout, and extraction assumptions that have not
   been proven by the existing unit tests.
6. The current Rootless test coverage validates only the final directory
   layout; it does not exercise bootstrap, payload packaging, PRoot spawn, or
   first-session creation.

Missing packaged executables are therefore a strong repository-level
hypothesis, not a substitute for reproducing the user's actual failure. Capture
the real error before deciding which failures are active on the device.

## Implementation requirements

### Packaged PRoot runtime

If the expected PRoot files are absent or unusable:

- provide an Android/Bionic-compatible ARM64 PRoot executable and its matching
  loader through a reproducible, reviewable build or artifact-provenance path;
- pin the upstream source/release and checksum;
- record and package the applicable license and notices;
- do not commit or execute an unexplained third-party binary;
- do not download executable code into writable app storage at runtime;
- keep NativeExecutableLoader as the only resolution policy;
- preserve the allow-list and canonical-path containment checks;
- package the executable payloads so Android extracts them under
  ApplicationInfo.nativeLibraryDir with the exact names expected by the loader;
- verify executable permission and actual process launch on the target;
- support ARM64 first, matching the current Rootless product contract;
- fail clearly on unsupported ABIs instead of silently using Native or AVF;
- ensure Android 16 KiB page compatibility where applicable and verify the ELF
  program headers with an available readelf-compatible tool;
- integrate the native build with the existing ARM64 Ubuntu host strategy
  rather than assuming Google's x86_64 NDK host executables can run.

Do not weaken targetSdk, set a broad extraction exception, use hidden APIs, or
move executable payloads into filesDir as a shortcut.

### Bootstrap correctness and recovery

Verify and fix the bootstrap path even if missing PRoot payloads are the first
failure:

- the pinned URL, release ID, archive root, and SHA-256 must match a real,
  immutable upstream artifact;
- keep HTTPS, byte limits, checksum verification, safe path containment, and
  link-escape defenses;
- correctly handle legitimate Debian archive paths and links without accepting
  traversal, host-absolute writes, unsafe device nodes, or arbitrary special
  files;
- avoid destructive replacement of a known-good rootfs;
- clean incomplete downloads and staging directories;
- make retry idempotent after process death, download failure, checksum failure,
  or interrupted extraction;
- serialize concurrent prepare/install requests in the runtime owner;
- keep blocking network and extraction work off Binder and UI threads;
- preserve a useful causal error for the UI instead of replacing it with a
  generic setup-required message;
- do not add network-dependent unit tests. Use injected dependencies and small
  deterministic archive fixtures where needed.

### Session start and lifecycle

Verify the complete PRoot invocation:

- command versus argv[0] handling through PtyProcess/JNI;
- PROOT_LOADER and host environment;
- guest root, bind mappings, HOME, TMPDIR, PATH, TERM, cwd, and shell;
- readable/executable guest shell and dynamic linker;
- PTY output delivery and early-exit reporting;
- session registration only after a valid controller is ready;
- no silent fallback to Native or AVF;
- UI detach/recreation must not terminate the PRoot process or PTY;
- an actual process death must not be represented as a live session.

Do not add a delay, swallow an exception, or mark the runtime Ready before the
required executable/rootfs/controller state is valid.

### Tests and observability

Add focused tests that fail before the fix and pass after it. Cover the
root-cause boundary and, where practical:

- APK/native payload naming or presence;
- executable-loader success/failure with exact diagnostics;
- archive layout, checksum, path traversal, safe links, size limits, staging,
  and retry behavior;
- backend state transitions and preservation of the causal failure;
- Rootless session registration and no-fallback behavior.

Add concise structured logging around Rootless phases if current logs cannot
distinguish them. Do not log secrets, full environment maps, private file
contents, or unbounded stack traces. User-visible messages should identify the
failed phase and a safe retry/action.

Update README.md and the relevant architecture/runtime/security/package
documents if packaging, bootstrap behavior, limitations, or build requirements
change. Remove claims that remain untrue.

## Acceptance criteria

### Build and package

- The ARM64 debug APK builds on the declared Ubuntu 24.04 aarch64 host.
- The APK contains the exact Rootless native payloads required by
  NativeExecutableLoader.
- The packaged payloads resolve from nativeLibraryDir, pass containment and
  executable checks, and have verified compatible ELF architecture/alignment.
- Existing Native startup still works.

### First Rootless launch

On a clean supported ARM64 test environment with network access and sufficient
space:

1. select Rootless Debian;
2. observe truthful download/install progress;
3. complete checksum verification and safe atomic installation;
4. create and attach a Rootless PTY session;
5. receive an interactive shell without root, ADB, AVF, or a manual file
   picker.

Inside that session, collect concise output from:

~~~sh
cat /etc/os-release
printf 'rootless-ok\n'
command -v apt || command -v apt-get
apt-get update
~~~

Do not treat apt-get update as passed if network access was unavailable. Report
that condition separately while still proving local shell startup.

### Lifecycle and retry

- Destroy/recreate or stop/start the Activity without terminating the Rootless
  process; reattach to the same session and observe continued output.
- A deliberately interrupted or failed bootstrap leaves no state that requires
  clearing all app data.
- Retry resumes safely or restarts only the incomplete app-owned installation.
- Network, checksum, storage, unsupported-ABI, and executable-payload failures
  show distinct actionable messages.
- Native and AVF behavior is not regressed.
