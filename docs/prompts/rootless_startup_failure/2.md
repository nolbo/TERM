## Requirements

1. Follow the bounded inspection, implementation, validation, and MCP rules in
   `AGENTS.md` and `1.md`; do not replace the requested fix with a plan-only
   response.
2. At startup, record `git status --short --branch`, the current branch, the
   current `HEAD`, and `git remote -v`. Fetch `origin` without modifying the
   worktree, then confirm the checked-out history contains this directive.
3. Preserve all pre-existing and unrelated worktree changes. Attribute every
   intended diff before staging it.
4. Complete the smallest coherent fix, its meaningful tests, and any required
   documentation. Inspect the final diff and run `git diff --check` plus the
   validation required by `1.md`.
5. Stage task-owned paths explicitly. Do not use broad staging such as
   `git add .` or `git add -A` when any unrelated or uncertain change exists.
6. Create one focused commit after validation. Use the subject
   `fix: repair Rootless Debian startup` unless the final implementation makes
   a more precise conventional subject clearly preferable.
7. Push the checked-out branch with `git push origin HEAD`. If the branch has
   no upstream, use `git push -u origin HEAD`. Never force-push.
8. Verify the push by resolving the remote branch after the command and
   confirming that it contains the local commit. Do not infer success only from
   the absence of a local Git error.

## Failure and divergence handling

- A failing check introduced by this task, an unresolved Rootless startup
  defect, or an incomplete implementation blocks commit and push. Continue the
  fix while safe; otherwise stop and report the exact blocker without creating
  a misleading success commit.
- A clearly pre-existing failure, an unavailable suitable Android target, or a
  privileged/manual acceptance step does not automatically block commit and
  push when all runnable relevant checks pass and the change has sufficient
  source/test evidence. Report the limitation precisely.
- If the push is rejected as non-fast-forward, fetch and inspect the divergence.
  A rebase of the newly created task commit is authorized only when unrelated
  work is preserved, the worktree is safe, and the rebase is conflict-free.
  Re-run affected validation after rebasing, then retry the normal push once.
  If those conditions are not met, stop and report the divergence; do not
  force-push, discard work, or guess through conflicts.
- If authentication, branch protection, repository permissions, or network
  policy blocks the push, preserve the local commit and report the exact
  command and concise error. Do not weaken remote protections or expose
  credentials.
- Do not amend, squash, reset, clean, or stash unrelated work. Do not create a
  pull request unless the user separately requests one.

## Validation

Run the focused checks, affected module tests, canonical repository
verification, and available Android/Replicant runtime checks required by
`1.md`. After committing and pushing, capture concise output from:

~~~sh
git status --short --branch
git show --stat --oneline --decorate --no-renames HEAD
git rev-parse HEAD
git ls-remote --heads origin "$(git branch --show-current)"
~~~

Compare the local SHA with the remote result. If the remote uses an unexpected
ref mapping or the branch name is empty, resolve it safely and report what was
verified instead of constructing a destructive command.
