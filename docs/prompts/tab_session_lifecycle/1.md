# Fix tab-close isolation and the zero-tab lifecycle

- Session: `tab_session_lifecycle`
- Index: `1`
- Intent: `implement`

## Execution profile

- Recommended model class: strongest available coding model
- Recommended reasoning effort: high
- Escalation condition: use maximum reasoning only if a reproducible cross-process or out-of-order session-state race remains after a high-effort implementation and device run; do not escalate for ordinary compilation or test failures

## Goal

Fix the tab-close lifecycle end to end so that:

1. explicitly terminating one tab affects only that tab's exact session;
2. every other Native, Rootless, or AVF session keeps the same live process, output stream, terminal contents, scrollback, dimensions, and usable input path;
3. terminating the final tab leaves the Activity in a stable zero-tab/empty state instead of closing, crashing, stopping the runtime service, or immediately creating a replacement session;
4. a new session can be created normally from the zero-tab state; and
5. Activity recreation, UI detach, task switching, and service rebinding never become implicit session- or runtime-termination signals.

This is an implementation task. Diagnose the observed behavior, implement the fix, add regression coverage, validate it on a suitable Android target when available, update relevant documentation, then commit and push the verified task-owned changes.

In the current `main` snapshot, verify these observations before relying on them:

- `MainActivity.terminate()` removes the target client adapter and calls `terminateSession(id)` before an authoritative completion result is available.
- `renderSessions()` chooses another active ID from a replacement list, while `renderRuntimeState()` may automatically create a Native session whenever the list is empty.

- `closeSessionClient()` closes every registered controller and clears all sessions; it must remain restricted to explicit runtime shutdown or genuine service destruction, never ordinary tab closure or a zero-session state.

Treat these as concrete hypotheses to prove or disprove with logs, focused tests, and runtime observation. Do not patch around the symptoms without locating the actual failing sequence.

## Requirements

### 1. Keep tab, session, runtime, and Activity lifetimes separate

Maintain these distinct operations:

- select/attach a tab: display and attach to one existing session;
- leave the screen or recreate the Activity: detach UI listeners/renderers only;
- explicitly terminate a session: terminate exactly one session ID after the existing destructive confirmation;
- explicitly stop a runtime: the only ordinary user action allowed to close all sessions owned by that runtime;
- Android process death: detect and report actual loss honestly.

Do not call or indirectly trigger `Activity.finish()`, `finishAndRemoveTask()`, `stopService()`, `stopSelf()`, `stopRuntime()`, `closeSessionClient()`, controller-wide `close()`, or equivalent global cleanup merely because a tab was closed or the session count reached zero.

Preserve the existing confirmation that makes process termination explicit. If UI copy says only “close” while the action sends a kill signal, revise it so the destructive effect remains unmistakable. Do not silently change explicit termination into a hidden detach operation.

### 2. Make single-session termination isolated and authoritative

Use the exact immutable session ID captured by the confirmed close request. A delayed callback, recomposition, selection change, or tab reorder must not redirect termination to the newly active session.

The runtime service/session registry is authoritative. Do not permanently remove a tab or dispose its client state based only on an optimistic UI assumption. Represent an in-flight termination explicitly, disable duplicate termination for that ID, and reconcile the UI after authoritative success. On failure, keep or restore the tab, clear the pending state, and show the operation error without touching sibling sessions.

At every layer, a successful `terminate(sessionId)` must:

- route to exactly one owning runtime controller;
- remove and signal only that controller entry;
- leave sibling controller entries and the controller itself alive;
- remove the owner mapping only after success;
- tolerate a duplicate or stale UI response without escalating into global cleanup; and
- publish one coherent post-operation session snapshot.

Do not solve the issue by recreating unaffected processes, terminal sessions, backends, or renderers. Their stable IDs and underlying shell PIDs must remain unchanged.

### 3. Prevent false or stale session-list replacement

Audit every caller of session refresh and every source of `onSessionsChanged`.

The UI must never receive an older snapshot after a newer one, and a temporary failure to list one optional runtime must not be represented as authoritative deletion of that runtime's previously live sessions. Implement the smallest robust mechanism compatible with the repository, such as serialized refreshes plus a monotonic revision/generation, or an equivalent single-writer state pipeline.

Requirements:

- session mutations and the snapshot they publish have a defined order;
- stale refresh results cannot overwrite a newer result;
- a per-runtime `list()` failure retains the last known state for that runtime or marks it unavailable/stale without silently publishing false deletions;
- a confirmed controller disconnect or PTY-owner death is reported as actual session loss rather than retained forever;
- callbacks identify enough context to reject stale UI results if AIDL delivery can be reordered; and
- the service does not broadcast an empty list merely because its registry transport is temporarily reconnecting when the owner is expected to survive.

If AIDL or protocol changes are necessary, keep them typed, bounded, backward-consistent inside this repository, and update all implementations and tests in the same change. Do not expose backend-specific details to the UI.

### 4. Preserve unaffected terminal presentation state

Closing one tab must not clear the client-side terminal objects, emulator buffers, selection state, scrollback, or adapters belonging to any other session.

When the active tab is terminated:

- choose the replacement deterministically from the previous visible order: prefer the tab now occupying the closed tab's index, otherwise the preceding tab;
- attach the renderer to that existing client session without recreating it;
- do not duplicate transcript replay or reset the shell prompt;
- keep output consumption active for background tabs according to the existing architecture; and
- ignore late output/exit callbacks for the removed ID without affecting another ID.

When a non-active tab is terminated, the active tab and its focus, IME state, viewport, scrollback, and renderer must remain unchanged.

Review `TerminalView.attachSession()` and the remote backend callback lifecycle. Clear or replace a reference to a terminated client session safely; never let a callback from it mutate the newly selected terminal.

### 5. Implement a real zero-tab state

After the user terminates the last session:

- keep `MainActivity` visible and responsive;
- show a clear Material 3 empty state with an action to create a new session and continued access to Settings;
- do not compose an interactive terminal renderer or terminal extra-key row with no active session;
- hide the IME and release terminal focus safely;
- keep the runtime service alive in `READY` or `IDLE` according to its actual state and existing foreground-service policy;
- show an accurate zero-session notification/state rather than stopping the service;
- do not automatically create a replacement Native session in response to the termination snapshot, an `IDLE` callback, recomposition, Activity recreation, or service rebinding; and
- allow the user to create any available runtime type from the empty state.

Preserve immediate first-use startup if it can be distinguished reliably from an intentional zero-tab state. It is acceptable to replace unconditional automatic Native creation with an explicit empty-state “New session” action if that is the cleanest correct design. Under no circumstance may asynchronous state callbacks create an unwanted replacement after the user closed the last tab.

Returning to the app after backgrounding or recreating the Activity must query the service as source of truth. If the service still has zero sessions, remain in the zero-tab state. If live sessions exist, restore the selected valid session or choose a deterministic one without restarting its process.

### 6. Preserve explicit global-stop behavior

Do not weaken an existing explicit runtime stop action. If the user explicitly stops a runtime, its documented destructive behavior may terminate the sessions it owns after confirmation. This task changes tab/session closure and zero-tab behavior only.

## Required automated regression coverage

Add tests at the layer where each invariant can fail. Extract a small pure UI state reducer if needed instead of trying to prove all selection behavior through Activity internals.

At minimum cover:

1. three sessions in one controller: terminating the middle ID removes only it; the other descriptors, controller, and connection remain alive;
2. sessions across Native and Rootless/AVF controllers: terminating one runtime's session does not close, hide, or recreate the other runtime's session;
3. a controller `list()` failure does not turn its last known healthy sessions into an authoritative empty deletion while other controllers refresh;
4. an older delayed refresh cannot overwrite a newer post-termination snapshot;
5. duplicate termination of the same ID cannot affect a sibling or close the registry;
6. closing the active tab selects the deterministic adjacent session and preserves its existing client terminal object;
7. closing a background tab leaves the active selection and renderer identity unchanged;
8. closing the last tab produces an empty UI state with no automatic create effect and keeps New Session/Settings actions available;
9. an operation failure clears the pending-close state, reports the error, and preserves the target and siblings;
10. Activity detach/rebind with zero, one, and multiple sessions does not invoke terminate or runtime stop; and
11. controller-wide close/global runtime stop remains reachable only through its explicit lifecycle path.

Where practical, add regression coverage for late output and exit events from a just-terminated ID so they cannot be delivered into the replacement tab's emulator.

## Required device and interaction validation

Use a suitable Android device/emulator when available. A successful build alone is not sufficient for this lifecycle task.

### Scenario A — same-runtime isolation

1. Create Native sessions A, B, and C.
2. In each, print a unique marker and shell PID, then run a counter such as `while true; do ...; sleep 1; done`.
3. Record B and C's PIDs, output progress, and visible scrollback.
4. Close A after the destructive confirmation.
5. Verify B and C retain the same PIDs, counters continue without restarting, their prior scrollback remains, input still works, and no duplicated transcript/prompt appears.
6. Close background session C while B is active and verify B does not lose focus, reset, or reconnect unnecessarily.

### Scenario B — cross-runtime isolation

When Rootless is available, run one Native and one Rootless long-running session. Terminate each in turn while observing the other. The surviving shell PID, output, working directory, and transcript must remain unchanged. Exercise AVF only when a correctly provisioned privileged target exists; do not claim stock-emulator AVF validation.

### Scenario C — zero tabs

1. Terminate the final session.
2. Verify the Activity remains visible with the empty state, no crash/ANR occurs, the terminal renderer and extra keys are absent, and no replacement session appears after several runtime callbacks.
3. Verify the `:vmhost` service/process remains in its accurate ready/idle state and its notification is accurate.
4. Background and foreground the app, rotate/recreate the Activity, and reopen it from Recents/launcher. It must remain a valid zero-tab state without an unwanted session.
5. Create a new Native session from the empty state and verify normal input/output.

### Scenario D — races and recovery

- double-tap or repeat the close action while termination is in flight;
- rotate or background the Activity while the confirmation or operation is pending;
- close an active tab while another session is producing rapid output;
- disconnect/rebind the UI process without killing `:vmhost`; and
- verify filtered logcat contains no fatal exception, service stop, controller-wide close, or sibling termination caused by the tab action.

Record exact observed results. Screenshots may establish the zero-tab UI, but use process/session IDs and logs to prove lifecycle isolation.

## Acceptance criteria

The task is complete only when all of the following are true:

- one confirmed tab termination reaches exactly one session ID and one owning controller entry;
- every sibling session keeps its original ID and shell PID, continues producing output, retains terminal contents/scrollback, accepts input, and is not reconstructed;
- transient per-runtime list failures and out-of-order refreshes cannot falsely delete or restore sessions in the UI;
- closing a non-active tab does not disturb the active renderer, focus, IME, or viewport;
- closing the active tab deterministically selects an adjacent existing tab without resetting it;
- closing the last tab leaves a responsive Material 3 zero-tab screen with New Session and Settings access;
- zero tabs do not finish the Activity, stop the service/runtime, close all controllers, or automatically create a replacement session;
- Activity recreation and service rebinding preserve the authoritative zero/one/many-session state;
- explicit runtime stop behavior remains separate and functional;
- required automated tests pass;
- device scenarios pass where supported, or the exact environment limitation is reported;
- relevant architecture/runtime/user documentation matches the implemented behavior; and
- the final diff contains no unrelated changes.
