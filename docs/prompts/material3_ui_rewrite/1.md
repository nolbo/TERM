## Goal

Replace the active `android-app` presentation layer with a cohesive Material
Design 3 UI implemented with Jetpack Compose. Preserve all working terminal,
session, runtime, setup, settings, diagnostics, sharing, and crash-report
behavior while replacing the application-owned Terminal Grid view system.

This task intentionally changes the design system permitted by the UI contract
in `AGENTS.md`. It is a functional implementation task, not a mockup, a plan,
or a partial theme overlay.

## Architecture decision

The new active UI MUST use Jetpack Compose with the stable Material 3 component
library. Do not build a second Material-styled XML UI or leave two competing UI
stacks.

1. Retain the existing Activity and intent boundaries unless a concrete source
   constraint makes a small consolidation safer. A single-Activity/navigation
   rewrite is not a goal.
2. Replace each visible Activity's ViewBinding content with Compose content
   hosted by `setContent` and the shared application theme.
3. Embed the existing terminal renderer through a lifecycle-safe `AndroidView`.
   Keep its instance, callbacks, input, resize, selection, scroll, and terminal
   backend behavior stable across recomposition. Do not rewrite the emulator or
   renderer as a Compose canvas.
4. Hoist renderable UI state and send typed user actions downward, but do not
   move PTY, process, installation, or VM ownership into a composable,
   `ViewModel`, Activity, dialog, or navigation object.
5. Service state remains authoritative. Compose state is a projection and must
   be rebuilt after Activity recreation or service reattachment.
6. Remove obsolete XML layouts, ViewBinding configuration, custom Terminal
   Grid widgets, style resources, drawables, and dependencies only after
   proving they have no active references. Do not retain dead compatibility
   wrappers as a permanent parallel system.
7. Use stable, non-experimental Material 3 APIs. Do not adopt Material 3
   Expressive or unrelated adaptive-navigation libraries as part of this task.

## Material 3 design system

Implement one reusable Compose theme and component layer for the active app.

### Color and theme

- Follow the system light/dark setting rather than forcing the complete app UI
  dark.
- Apply Android dynamic color on supported devices and provide deliberate
  light and dark fallback color schemes based on the existing mint product
  accent and neutral surfaces.
- Use semantic Material roles such as primary, on-primary, surface,
  surface-container, on-surface, outline, error, and their variants. Do not use
  raw colors as ad hoc component state.
- Preserve the terminal canvas and user-selected terminal palette independently
  from application chrome. Dynamic application color must not recolor terminal
  output, ANSI colors, cursor, or selection unexpectedly.
- Configure edge-to-edge status and navigation bars with icon contrast derived
  from the active color scheme. Avoid obsolete hard-coded dark icon policy.

### Typography, shape, spacing, and motion

- Use the Material 3 type scale for application text. Keep monospace limited to
  terminal content, extra-key labels where fixed cells matter, and selectable
  diagnostic/crash payloads.
- Use consistent Material 3 shape and spacing tokens; retain a compact layout
  appropriate for a terminal without creating undersized controls.
- Use Material motion sparingly for screen, dialog/sheet, and state changes.
  Honor the platform animator-duration setting and avoid animations that reset
  terminal focus, selection, scroll position, or session attachment.
- Reuse suitable vector icons with correct theme tint and semantics. Do not add
  an icon font, remote asset dependency, or decorative icon for every label.

### Reusable components

Prefer standard Material 3 components over application-owned replicas,
including top app bars, buttons, icon buttons, cards, list items, switches,
radio controls, text fields, dialogs or modal bottom sheets, progress
indicators, snackbars, dividers, and tab or selectable-chip patterns. Create a
small wrapper only when a repeated terminal-specific contract cannot be
expressed clearly with a standard component.

## Screen requirements

### Initial setup

- Present Android Native, Rootless Debian, and AVF Debian as distinct choices
  with concise compatibility, setup, and privilege descriptions.
- Keep Native as the immediate permissionless path, Rootless as the broad
  permissionless Linux path, and AVF as optional and privileged.
- Give the primary next action clear emphasis and keep local AVF image selection
  visibly separate from Rootless installation.
- Support narrow portrait, landscape, large font, and scrolling without clipped
  actions.

### Terminal

- Preserve the three functional regions: session/navigation chrome, the native
  terminal renderer, and two fixed rows of extra keys.
- Express session selection with a horizontally scrollable Material 3 pattern.
  Each session must show its runtime and title, expose an accessible explicit
  terminate action, and show active state without relying on color alone.
- Keep New session and Settings as discoverable 48 dp actions with content
  descriptions. Do not reduce the terminal viewport with decorative chrome.
- Preserve terminal focus, IME input, hardware keyboard input, modifier keys,
  scrollback, text selection, resize callbacks, and renderer attachment while
  tabs or surrounding Compose state update.
- Closing a UI screen or detaching a renderer must not terminate work. Session
  termination still requires the existing explicit destructive action and
  runtime acknowledgement.

### New session and Rootless setup

- Use an accessible Material 3 dialog or modal bottom sheet for runtime
  selection. Show availability, permission/setup implications, and failure
  state in text rather than color alone.
- Keep runtime selection explicit; never redirect a failed Rootless or AVF
  request to another runtime.
- Show Rootless preparation with a Material progress indicator, concise current
  status, error detail, retry, and close actions.
- Dismissing the status surface must not cancel a runtime-owned installation.
  Reopening it must render current service state rather than stale local state.

### Settings

- Rebuild overview and detail screens with Material 3 top app bars, section
  hierarchy, list items, supporting text, and controls appropriate to each
  value.
- Use switches for booleans, outlined text fields with supporting/error text for
  free input, single-choice dialogs with radio controls for bounded values, and
  clear trailing affordances for navigation or system actions.
- Make an entire setting row activate its control where that is unambiguous,
  while preserving screen-reader semantics and preventing double toggles.
- Preserve when each setting takes effect: terminal appearance on return,
  runtime resources on next start, and shell defaults on new sessions.

### Diagnostics and crash report

- Use Material 3 structure and actions while retaining selectable monospace
  payloads.
- Keep diagnostics read-only and retain refresh as a clear top-app-bar action.
- Keep Copy as the primary crash-report recovery action and Dismiss/Close as a
  lower-emphasis action. Do not discard diagnostic data accidentally.

### Transient and system-entry behavior

- Represent loading, empty, disabled, success, and error states deliberately.
  Do not leave raw placeholder text over the terminal after a successful attach.
- Prefer a Material snackbar for in-app transient feedback when a visible host
  exists. A short-lived exported/system entry Activity may use an appropriate
  system-level fallback without inventing a permanent screen.
- Preserve share-intent security and runtime behavior; this UI task does not
  broaden what guest environments can access.

## Accessibility and adaptive behavior

- Every interactive target must be at least 48 by 48 dp, including icon and
  session-close actions. Extra-key cells may share fixed row height only when
  the complete touch target remains usable.
- Provide action-oriented labels for icon buttons and meaningful screen-reader
  semantics for selected tabs, progress, disabled choices, errors, and grouped
  controls.
- Do not encode selection, availability, or errors by color alone.
- Verify contrast for fallback light and dark schemes and for at least one
  dynamic color scheme.
- Avoid fixed text heights. Important screens must remain usable at large font
  scale, in narrow portrait, and in landscape with IME and system bars visible.
- Preserve logical traversal order, keyboard focus, back navigation, and RTL-safe
  start/end layout behavior. The terminal character grid itself may remain LTR
  where required for correct emulation.
- Move user-visible strings introduced or touched by the rewrite into Android
  string resources. Do not hard-code new Korean or English UI copy in Kotlin.
