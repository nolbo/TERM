# 1.4.0 출시 검증 기록

작성일: 2026-10-22. 사용자는 세 배포판의 EXT4 전환 구현 후 이미지 제작·검증·배포와 정식 TERM·TERM Preview 두 채널 배포를 요청했다. 실제 AVF 기기 검증은 사용자의 명시적 지시로 생략한다. 기존 설치 환경을 덮어쓰거나 자동 전환하지 않는다.

## 구현과 사전 검증

- 구현 커밋: `2444b97` — 이미지 v2의 완전한 EXT4 루트, v1 부팅 호환, 형식별 업데이트 선택·유지보수·복구 및 확장 데이터 이전.
- Python 이미지 검사 121개 및 최종 이전 검사, 표준 APK 빌드·런타임·이미지·AVF 모듈 테스트 통과. 로컬 ARM64 AAPT2의 이전 경로 문제는 기존 9.3 도구의 임시 실행 경로 지정으로 해결했으며 저장소 호스트 설정은 유지했다.
- 새 이미지가 필요한 범위: 세 배포판의 initrd·fstab·루트 디스크 구성·유지보수·이전·부팅 게이트. 이전 승인 이미지로는 전달되지 않으므로 새 이미지를 제작한다.
- 커널 소스·설정·제작 스크립트는 성공 실행 `39715151260`의 `6dd30332eacdb0c64bee00259fee62eaaf64d2a1`과 동일하다. 해당 실행의 만료되지 않은 커널 번들을 재사용하며 성공한 동일 저장소 dev 제작, 공유 이력과 동일 레시피를 확인하고 기존 제작기가 번들 해시·실제 커널 설정을 다시 검사한다.

로컬 표준 검증 명령(성공):

```sh
JAVA_HOME=/usr/lib/jvm/java-17-openjdk-arm64 ./gradlew \
  :android-app:assembleDebug :android-runtime:testDebugUnitTest :image:test \
  :aosp-avf-runtime:testDebugUnitTest \
  -Pandroid.aapt2FromMavenOverride=/tmp/term-ext4-build-tools/aapt2 --console=plain
```

커널 재사용 검사 추가 후 실제 r2 제작 CI의 Python 이미지 검사는 122개 모두 통과했다. 이 기록에 나온 AAPT2 임시 경로는 해당 ARM64 검증 호스트의 실행 도구이며 앱이나 이미지의 배포 경로가 아니다.

## 이미지 및 앱 배포

첫 r1 제작은 UUID 변경 전에 필요한 파일시스템 검사가 없어 중단됐다. Ubuntu 실행 [39746727302](https://github.com/nolbo/TERM/actions/runs/39746727302)의 `tune2fs`가 `This operation requires a freshly checked filesystem`를 보고했다. 같은 코드의 Debian 실행 중단을 요청했으며 Arch는 이미 종료되어 중단 요청을 적용하지 않았다. 게시된 r1 이미지는 없다. 기존 태그·이력을 보존하고 수정된 새 r2 태그로 제작한다.

실제 제작과 같은 metadata checksum 설정과 마운트 후 검사 시각을 재현한 EXT4 fixture에서 기존 순서의 실패를 재현했다. 검사 → UUID 변경 → 확장 순서로 수정한 뒤 EXT4 이전 검사 4개가 통과했다.

공개된 커널 재사용 변경에 대한 Jev 게이트는 주장 3개를 verified로 분류했지만 자동 통과하지 않았다(safe_to_apply 0.54, blast_radius confidence 0.22). 구체적인 결함이나 모순은 제시하지 않았다. 출처·레시피 실제 검사와 소스 검토를 수행했고 실제 제작기의 번들 검증·부팅 게이트를 계속 요구한다.

세 r2 이미지를 공유 dev의 `ae6caa804744f832c911c31cce2644e5a4ae6689`에서 제작·게시했다. 각 실행의 image·apk·publish 게이트가 성공했다. image 단계의 Python 이미지 검사, 두 번의 EXT4 루트·패키지·컨테이너 기능 부팅과 두 번의 정상 systemd/vsock 부팅, 두 번째 부팅의 공유 파일 I/O·호스트 소유자 상실 정리가 통과했다. 사용자 요청에 따라 실제 Android AVF 기기는 사용하지 않았다.

각 제작 원본의 catalog·manifest·provenance·SHA256SUMS를 보관했다. CI의 공개 검증 이후 로컬에서도 `verify-avf-release.py --metadata-only --expected-commit ae6caa804744f832c911c31cce2644e5a4ae6689 --require-private-shares-boot --require-container-kernel --approve <임시 카탈로그>`로 세 이미지의 무인증 공개 manifest와 다섯 gzip 산출물을 스트리밍하고 압축 해제 SHA-256을 확인했다. 세 검증 모두 종료 코드 0이며, 검증된 핀만 `image/catalog-approved.properties`에 병합했다. 원본 디스크 전체를 로컬에 저장하거나 기존 환경을 변경하지 않았다.

앱 배포 원본은 세 r2 승인 카탈로그를 포함한 공유 dev의 `9f9381c5637e2569c0716ec323faebc8ca235581`이다. TERM Preview는 공식 서명·게시 실행 [39753173586](https://github.com/nolbo/TERM/actions/runs/39753173586)에서 성공했고 [dev-9f9381c5637e2569c0716ec323faebc8ca235581](https://github.com/nolbo/TERM/releases/tag/dev-9f9381c5637e2569c0716ec323faebc8ca235581)로 공개됐다(`isDraft=false`, `isPrerelease=true`).

무인증 공개 다운로드로 Preview APK의 26,817,844 bytes와 SHA-256 `70afe0e272b5d9c3c8e6b1fc572380ee3237e99cff0cffdd8bc2238326671162`를 확인했다. 실제 APK의 패키지는 `dev.terminal.app.prerelease`, 이름은 `TERM Preview`, 버전은 `1.4.0+dev.1000095.9f9381c5637e`(1000095), minSdk는 31이다. AAPT2로 확인한 두 Provider authority도 Preview 패키지 이름으로 분리되어 있다. 공개 패치 노트는 커밋된 `dev-latest.md`와 정확히 일치한다.

`verify-release-apk.py`로 다운로드한 두 채널 APK 모두의 기존 인증서 SHA-256 `7f639e70cc1969415beab27cfb10db6d10bf553b1f956a2f9d68d55ebf3785ba`와 승인 카탈로그의 정확한 일치를 확인했다. 따라서 두 공개 APK 모두에 세 r2 이미지의 검증된 핀이 들어 있다.

같은 원본의 정식 TERM 서명·게시 실행 [39755109882](https://github.com/nolbo/TERM/actions/runs/39755109882)도 성공했다. [main-9f9381c5637e2569c0716ec323faebc8ca235581](https://github.com/nolbo/TERM/releases/tag/main-9f9381c5637e2569c0716ec323faebc8ca235581)로 공개됐으며 `isDraft=false`, `isPrerelease=false`다.

정식 APK 역시 무인증 공개 다운로드로 26,817,820 bytes와 SHA-256 `5c13c3021c17349e90573d80b2c133e54a9719fa2e5453f16f0e216c6feb469d`를 확인했다. 실제 APK의 패키지는 `dev.terminal.app`, 이름은 `TERM`, 버전은 `1.4.0+main.1000096.9f9381c5637e`(1000096), minSdk는 31이다. 두 Provider authority는 정식 패키지 이름으로 분리되어 있으며 공개 패치 노트는 커밋된 `main-latest.md`와 정확히 일치한다.

두 채널 모두 공식 CI의 빌드·단위 테스트·서명·게시가 성공했다. 공개 APK의 해시·서명·승인 이미지 목록·패키지·버전·앱 이름·minSdk·Provider authority 확인이 완료됐다. 기기 설치는 하지 않았다. 기존 AVF v1 환경은 자동 변환되지 않으며 EXT4 전환에는 사용자가 선택하는 전체 이미지 업데이트가 필요하다. 이전 세대는 복구를 위해 보존한다.

최종 Jev `jev_verify`는 공개 이미지 해시, 두 앱의 공통 소스·서명·카탈로그, 채널별 버전·게시 구분, 실기기 검증 생략의 네 주장을 모두 verified로 분류했다(모순·미지원 주장 없음). 이는 실제 검사 결과의 보조 검토이며 런타임 검증을 대신하지 않는다. GitHub MCP로 CI 작업 상태를 확인했고, 해당 연결 도구에 없는 workflow dispatch·release 조회·게시 관리는 기존 `gh` CLI를 사용했다.

## 검증 범위

실제 Android AVF에서의 부팅·이미지 이전·Docker/LXC·ReDroid·복구는 사용자 지시로 실행하지 않는다. QEMU 자동 제작 검증을 실제 기기 검증으로 간주하지 않는다. Discord 알림은 요청되지 않아 실행하지 않는다.
