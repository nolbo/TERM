# 1.4.0 출시 검증 기록

작성일: 2026-10-22. 사용자는 세 배포판의 EXT4 전환 구현 후 이미지 제작·검증·배포와 정식 TERM·TERM Preview 두 채널 배포를 요청했다. 실제 AVF 기기 검증은 사용자의 명시적 지시로 생략한다. 기존 설치 환경을 덮어쓰거나 자동 전환하지 않는다.

## 구현과 사전 검증

- 구현 커밋: `2444b97` — 이미지 v2의 완전한 EXT4 루트, v1 부팅 호환, 형식별 업데이트 선택·유지보수·복구 및 확장 데이터 이전.
- Python 이미지 검사 121개 및 최종 이전 검사, 표준 APK 빌드·런타임·이미지·AVF 모듈 테스트 통과. 로컬 ARM64 AAPT2의 이전 경로 문제는 기존 9.3 도구의 임시 실행 경로 지정으로 해결했으며 저장소 호스트 설정은 유지했다.
- 새 이미지가 필요한 범위: 세 배포판의 initrd·fstab·루트 디스크 구성·유지보수·이전·부팅 게이트. 이전 승인 이미지로는 전달되지 않으므로 새 이미지를 제작한다.
- 커널 소스·설정·제작 스크립트는 성공 실행 `39715151260`의 `6dd30332eacdb0c64bee00259fee62eaaf64d2a1`과 동일하다. 해당 실행의 만료되지 않은 커널 번들을 재사용하며 성공한 동일 저장소 dev 제작, 공유 이력과 동일 레시피를 확인하고 기존 제작기가 번들 해시·실제 커널 설정을 다시 검사한다.

## 이미지 및 앱 배포

첫 r1 제작은 UUID 변경 전에 필요한 파일시스템 검사가 없어 중단됐다. Ubuntu 실행 [39746727302](https://github.com/nolbo/TERM/actions/runs/39746727302)의 `tune2fs`가 `This operation requires a freshly checked filesystem`를 보고했다. 같은 코드의 Debian 실행 중단을 요청했으며 Arch는 이미 종료되어 중단 요청을 적용하지 않았다. 게시된 r1 이미지는 없다. 기존 태그·이력을 보존하고 수정된 새 r2 태그로 제작한다.

실제 제작과 같은 metadata checksum 설정과 마운트 후 검사 시각을 재현한 EXT4 fixture에서 기존 순서의 실패를 재현했다. 검사 → UUID 변경 → 확장 순서로 수정한 뒤 EXT4 이전 검사 4개가 통과했다.

공개된 커널 재사용 변경에 대한 Jev 게이트는 주장 3개를 verified로 분류했지만 자동 통과하지 않았다(safe_to_apply 0.54, blast_radius confidence 0.22). 구체적인 결함이나 모순은 제시하지 않았다. 출처·레시피 실제 검사와 소스 검토를 수행했고 실제 제작기의 번들 검증·부팅 게이트를 계속 요구한다.

새 r2 제작·게시 전이다. 성공 실행, 공개 manifest/산출물 검증, 승인 카탈로그와 최종 두 서명 APK의 포함 여부를 완료 후 기록한다.

## 검증 범위

실제 Android AVF에서의 부팅·이미지 이전·Docker/LXC·ReDroid·복구는 사용자 지시로 실행하지 않는다. QEMU 자동 제작 검증을 실제 기기 검증으로 간주하지 않는다. Discord 알림은 요청되지 않아 실행하지 않는다.
