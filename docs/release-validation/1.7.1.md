# TERM 1.7.1 출시 검증 기록

준비일: 2026-10-31. 사용자 요청에 따라 Userspace Linux 자체 엔진 개발 워크트리를 병합하지 않고 정식 TERM만 배포한다.

## 범위와 버전

직전 정식 `1.7.0+main.1000106.4b19bd5d5821` 이후 공유 dev의 AVF 세션·복구·입출력, Workspace 시작, 환경 종료와 이력 보존, 툴바 탭·이력 동작 수정을 포함한다. 기존 사용법과 데이터의 호환성을 유지하는 수정이므로 PATCH `1.7.0 → 1.7.1`을 적용한다. Jev의 버전 판단도 PATCH를 선택했다.

`.worktrees/userspace-engine`의 `work/userspace-engine` 브랜치와 미커밋 작업은 병합하거나 수정하지 않는다. 준비 시작 시 dev는 `dfe88c9b35cd80917de9c05e1e884acf6d821a74`, 별도 엔진 브랜치는 `c8f52c9ac88b2f1475dc4fbd73f4ef414edc52b5`였다. dev에 이미 있는 초기 엔진 실험 소스는 Gradle 제품 모듈·빌드 경로에 연결되어 있지 않으며, 배포 APK에도 엔진이 포함되지 않는지 확인한다. 이력을 재작성하거나 별도 출시 이력을 만들지 않는다.

## 이미지와 게시 절차

기존 unshared-20261028-r1 제작 이후 `guest/droid-sessiond`와 이미지 서비스·복구 구성이 바뀌었으므로 Debian·Ubuntu·Arch `session-20261031-r1`을 새로 제작한다. 기존 kernel producer `39715151260`의 번들은 제작 입력·실제 해시를 확인해 재사용한다. Google 원본 SHA-256은 기존 검증값 `765cec51cd3e16ea1745b7ac8f9b3816d21ab3ed069bea355a59e3ade6bdfc41`로 고정한다. 새 이미지의 제작·두 번의 정상 부팅·APK·익명 전체 다운로드 검증 후 승인 카탈로그를 dev에 커밋하고 정식 서명 APK에 포함한다. 설치된 환경은 자동 교체하지 않는다.

준비·승인·검증 기록 커밋에는 `[skip ci]`를 사용해 Preview 자동 배포를 방지한다. 공유 origin/dev 이력을 확인한 뒤 정상 fast-forward push만 사용한다. 이미지와 앱 CI는 dev에서 수동 실행하며 `notify=false`로 지정한다. main 브랜치·Preview 공개 상태를 변경하지 않는다.

## 검증 계획과 한계

표준 Gradle 빌드·단위 테스트와 변경 모듈 테스트, Rust 게스트 테스트, Python 이미지·업데이트 검사, redroid Android 15 ARM64에서 관련 앱·런타임 계측 검사를 수행한다. 최종 공개 APK의 공식 서명·패키지·버전·해시·카탈로그 및 최신 링크를 확인한다. redroid는 실제 특권 AVF 대상이 아니므로 `tests/integration/acceptance.sh`와 실제 AVF 수명·Doze 검증을 통과로 주장하지 않는다.

GitHub MCP는 원격 브랜치·CI 근거, android MCP는 기기·런타임 검증, replicant는 제공 가능한 UI 상호작용 확인, Jev는 버전 판단과 최종 검증 주장 검토에 사용한다. GitHub MCP에 없는 dispatch·태그·릴리즈 다운로드는 gh로 수행한다. 외부 API 변경이 없어 context7은 사용하지 않는다. 로컬 Git 쓰기와 네트워크는 샌드박스 밖의 승인된 실행이 필요하며 기존 캐시·도구체인을 유지한다.

## 이미지 제작 실행

제작 소스 `5efc7be7d2c689b957ff12fe60af20816b859b87`를 origin/dev에 정상 fast-forward로 푸시하고 원격 일치를 확인했다. 별도 엔진 워크트리를 병합하지 않았다. 세 불변 이미지 태그는 이 커밋을 가리킨다. Debian [41197253098](https://github.com/nolbo/TERM/actions/runs/41197253098), Ubuntu [41197256804](https://github.com/nolbo/TERM/actions/runs/41197256804), Arch [41197260215](https://github.com/nolbo/TERM/actions/runs/41197260215)를 `publish=true`, `notify=false`, `kernel_run_id=39715151260`으로 실행했다.

재사용 커널의 전체 번들 검증과 제작 입력 비교가 통과했으며 실제 vmlinuz SHA-256은 기존 승인 이미지와 같은 `fa4f0fc22c316d24a417e5620e915c626ab246ef5c190b557d38c136955357ee`다. 이미지 CI도 출처와 동일 레시피 검증을 통과했다. 새 이미지의 공개·카탈로그 승격 결과는 완료 후 아래에 기록한다.

## 첫 이미지 제작의 정상 부팅 검사 실패와 수정

Debian·Ubuntu r1 제작은 정상 systemd 부팅 후 `verify_offline_progress`의 첫 LIST 상태 검사에서 실패해 이미지 공개·APK 단계가 차단됐다. 32 MiB 출력 세션을 만든 후 소켓을 끊고 4초만 기다리던 검사였으며 실제 상태·종료 코드는 오류 메시지에 없었다. 현재 정상 부팅은 systemd 서비스 시작과 함께 QEMU TCG로 실행된다. Native 게스트 테스트는 같은 출력량의 disconnected/unread 상태에서 종료를 확인했지만 TCG 처리속도를 증명하지 않는다.

제품 코드는 바꾸지 않고 검사 대기를 30초로 조정하고 실제 상태·종료 코드를 오류에 포함했다. 전체 대기 중 연결을 끊어 두며, 재연결 후 첫 LIST에서 정확히 EXITED/7이어야 한다. 반복 LIST로 잠긴 작업을 진행시키거나 잘못된 종료 상태를 허용하지 않는다. 추가 회귀는 성공·계속 실행 중·잘못된 종료 코드를 모두 확인하고 첫 조회 실패 시 재시도가 없는지 검사한다. `test_systemd_boot.py` 9개와 Python 구문·diff 검사는 통과했다. 실제 TCG 성공 여부는 새 이미지 제작에서 확인한다.

원래 r1 태그와 실패 기록을 보존하고 수정 소스에는 새 불변 `session-20261031-r2` 이미지 ID를 사용한다. r1 산출물을 승인하거나 공개 앱에서 사용하지 않는다.

Arch r1도 같은 첫 LIST 검사에서 실패했다. Jev 수정 검토는 `safe_to_apply=0.64`, 테스트 판단 신뢰도 0.32로 자동 수락하지 않았고 구체적인 코드 모순은 제시하지 않았다. 실제 TCG 제작 검증을 추가 근거로 사용한다.

r2 제작 소스는 `b0a0191053bb7591570fb230e12be0b5b9257142`이며 원격 dev 일치를 확인했다. Debian [41198395097](https://github.com/nolbo/TERM/actions/runs/41198395097), Ubuntu [41198398665](https://github.com/nolbo/TERM/actions/runs/41198398665), Arch [41198401648](https://github.com/nolbo/TERM/actions/runs/41198401648)를 동일한 원본·커널 핀, `publish=true`, `notify=false`로 실행했다.

## Debian의 고정 시간 검사 한계와 독립 완료 관측

r2의 Ubuntu·Arch는 정상 부팅 검증을 통과했으나 Debian은 30초 뒤에도 LIST가 `state=1, exitCode=-1`을 반환해 공개가 차단됐다. 네이티브 32 MiB 회귀는 disconnected 152 ms·unread 169 ms에 종료했다. 이 결과만으로 Debian TCG 지연과 제품 결함을 구분할 수 없어 고정 대기만 계속 늘리지 않는다.

검사는 기존 독립 TFT1 파일 전송 서비스(40505)를 통해 임의 토큰 완료 파일을 관측하도록 보강했다. 32 MiB 출력이 성공한 뒤에만 완료 파일을 쓰며, 파일의 정확한 내용·크기·SHA-256과 ACK를 검증한다. 최대 120초 동안 파일을 기다리는 동안 터미널 40500 연결은 계속 닫혀 있다. 완료 이후 1초의 종료 수집 시간을 두고 첫 LIST에서 여전히 EXITED/7을 요구한다. 완료 파일이 없거나 잘못되면 터미널 재연결 없이 실패한다. 기존의 공유 디렉토리 기능을 켜거나 제품 게스트 코드를 바꾸지 않는다. 정상 부팅의 폐기용 디스크만 사용한다.

파일 채널·프레임·해시 거부, 누락 파일의 제한된 대기, 완료 없는 터미널 재연결 방지, 첫 LIST 상태 검사를 포함해 `test_systemd_boot.py` 12개와 Python 구문·diff 검사가 통과했다. Debian만 새 불변 r3로 제작하며, 제품 게스트·커널이 같은 Ubuntu·Arch r2 검증 산출물은 재사용한다. 최종 성공 여부는 새 Debian 정상 부팅 검사에서 판단한다.

Debian r3 [41199860170](https://github.com/nolbo/TERM/actions/runs/41199860170)는 소스 `312353e09c272bc6a1785ba631218bf7cbf2f3c0`에서 시작했으나 코드 대조 중 미존재 파일의 TFT1 status=1 처리 누락을 발견해 제작 초기에 취소했다. 아직 없는 표식은 제한된 대기 안에서 재시도하고, 잘못된 프레임·크기·내용·해시는 계속 거부하도록 수정했다. 표식은 임시 파일을 쓴 뒤 rename으로 공개해 쓰기 중인 파일을 관측하지 않는다. 실제 서비스의 오류 응답과 일치하는 회귀를 보완해 12개 검사를 다시 통과했다. r3 태그는 보존하고 최종 Debian 목표를 새 r4로 옮긴다. 제품 게스트 코드는 바뀌지 않았다.

Debian r4는 제작 소스 `e596d493b226f01ba386e27f5ffe4cd0da3b1d00`, 실행 [41200077556](https://github.com/nolbo/TERM/actions/runs/41200077556)으로 시작했다. 원격 dev와 불변 태그 일치를 확인했다. 원본·커널 핀과 알림 비활성 설정은 동일하다. Ubuntu r2는 제작·부팅·카탈로그 APK·게시 후 익명 전체 다운로드 CI까지 성공했다. r2 이후에는 제품 게스트·커널·파일시스템 구성 변경 없이 호스트에서 실행하는 제작 검사만 바뀌었다.

## 공개 이미지 검증 결과

Ubuntu·Arch r2의 제작·두 번의 정상 systemd 부팅·카탈로그 APK·게시 후 익명 전체 다운로드 CI가 모두 성공했다. 이후 공개 URL에서 인증 없이 메타데이터와 다섯 압축 산출물을 읽어 원본 크기·SHA-256, 제작 소스, 커널, 정상 부팅 provenance를 재검증한 결과만 승인 카탈로그에 반영했다.

- ubuntu: `avf-ubuntu-session-20261031-r2`, manifest SHA-256 `170d0ddb964d941219d9826a50275c041df77366740648d26562fc43f26533cb`, source `b0a0191053bb7591570fb230e12be0b5b9257142`.
- archlinux: `avf-archlinux-session-20261031-r2`, manifest SHA-256 `45622132e262efafaf367d1821ca694d7e02eb457310569b2abf852535bd86e7`, source `b0a0191053bb7591570fb230e12be0b5b9257142`.

Debian r4의 제작과 두 번의 정상 부팅 검사가 통과해 검증 산출물의 비공개 staging 단계로 진행했다. 이 검사는 터미널 소켓이 닫힌 동안 32 MiB 출력 성공 뒤의 원자적 완료 표식을 독립 TFT1 채널로 확인하고, 첫 LIST의 EXITED/7도 검증한다. 게스트 제품 코드 변경 없이 고정 시간 판단을 실제 완료 관측으로 교체해 통과했으며, TCG 처리시간이나 실제 Android AVF 성능을 보장하는 결과로 확대하지 않는다.

Debian r4의 카탈로그 APK·게시 후 익명 전체 다운로드 CI도 최종 성공했다. 별도 로컬 익명 다운로드에서도 메타데이터와 다섯 압축 산출물의 원본 크기·SHA-256 검증이 모두 통과했다. manifest SHA-256은 `cbb10eab7dd89128bf84f14ec97b2cd5c7c68d0cda4f74ef9ac7f35c293bd754`, 제작 소스는 `e596d493b226f01ba386e27f5ffe4cd0da3b1d00`이다. 정상 부팅 두 회 모두 LIST·패키지 초기화 포트·직접 재연결·연결 단절 중 출력 진행 검사를 통과했다.

검증된 Debian r4·Ubuntu r2·Arch r2를 `image/catalog-approved.properties`의 기본값으로 승격하고 이미지 절차·한국어 사용자 안내를 일치시켰다. 세 이미지 모두 같은 검증 커널을 사용하며 설치된 환경의 디스크는 교체하지 않는다. 정식 APK는 이 승인 카탈로그를 포함해 제작한다.
