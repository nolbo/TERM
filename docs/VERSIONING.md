# TERM 버전 승격 정책

## 적용 범위와 원칙

앱의 기본 버전은 `gradle.properties`의 `appBaseVersion`으로 관리하며
`MAJOR.MINOR.PATCH`를 사용한다. APK에 함께 들어가는 UI, Native·Rootless·AVF
연동의 사용자 관점 변경을 판단한다. 별도로 배포하는 Rootless payload와 게스트
이미지의 버전·프로토콜 번호는 해당 산출물의 정책을 유지한다.

판단 단위는 커밋 수나 작업 시간 대신 **같은 앱 채널의 직전 배포 이후 포함되는
전체 변경**이다. 여러 종류가 섞이면 가장 높은 승격을 한 번 적용하고, 하위 숫자는
0으로 초기화한다. 이미 정한 미배포 목표 버전은 기능 커밋마다 다시 올리지 않는다.
main 통합 시에는 직전 stable 이후 전체 범위를 다시 평가하되 이미 배포한 앱 기본
버전보다 낮추지 않는다. 배포된 버전의 의미와 과거 패치 노트를 소급 변경하지 않는다.

| 구분 | 승격 조건 | 예 |
| --- | --- | --- |
| PATCH | 기존 동작의 버그·보안 취약점 수정, 호환성을 유지하는 성능·접근성 개선. 새로운 사용자 기능이나 필수 이전 없음 | `0.2.0 → 0.2.1`: 복귀 시 불필요한 글꼴 로딩 제거, 특권 없는 AVF 설정 숨김 |
| MINOR | 기존 데이터와 지원 사용법을 유지하면서 사용자 기능·설정·실행 환경 지원 추가, 선택적 이전 제공 | `0.1.0 → 0.2.0`: 프로필 아이콘, 단축키 제스처, 하위 설정 검색 |
| MAJOR | 1.0 이후 지원 계약을 깨는 변경: 기존 데이터·프로필·명령/API 호환성 제거, 필수 수동 이전, 지원 Android/API·ABI 제거, 기존 무특권 흐름에 새 특권 요구 | `1.4.2 → 2.0.0` |
| 유지 | 문서·테스트·내부 정리·CI 재실행만 변경되고 사용자 동작·설치 호환성이 같음 | 기본 버전 유지, 새 배포는 새 `versionCode` |

보안 수정이라는 이유로 항상 PATCH를 택하지 않는다. 지원 계약을 깨면 해당
승격을 적용한다. 버전 승격은 데이터 삭제나 Native·Rootless 무특권 경로 훼손을
허용하지 않으며, 호환성 변경은 별도 설계와 명시적 이전·복구 안내가 필요하다.

## 0.x와 1.0.0

`0.x`는 안정화 중인 제품이다. 이 기간에는 호환성을 깨는 변경도 MINOR를 올리고
패치 노트에서 반드시 강조한다. PATCH에서 호환성을 깨지 않는다. 단순한 UI 배치
변경이나 메뉴 숨김은 저장 데이터·지원 기능의 계약을 깨지 않으면 MAJOR 사유가 아니다.

`1.0.0`은 다음을 모두 충족했다는 검증 기록이 있을 때 결정한다.

1. 일반 지원 Android 기기에서 Native 즉시 실행과 Rootless 설치·실행·패키지 사용이
   특별 권한 없이 동작한다. 지원 최소 API와 최신 지원 API의 검증 결과를 남긴다.
2. 생성·입출력·크기 변경·탭 전환·명시적 종료, 백그라운드 복귀·화면 재생성을
   검증한다. UI 분리 중 작업은 유지하고 실제 소유 프로세스 죽음은 손실로 보고한다.
3. 직전 서명 배포본에서 업데이트하여 설정·프로필·작업 파일·Rootless 환경 보존을
   확인한다. 필요한 이전의 중단·실패 복구도 검증하고, 지원 호환성 범위를 문서화한다.
4. 표준 빌드·관련 회귀 테스트·실기기 검증을 통과하고, 데이터 손실·보안 경계 우회·
   핵심 흐름 실패에 대한 알려진 차단 결함이 없다. 미검증 항목을 통과로 간주하지 않는다.
5. 사용자 안내, 보안·실행 환경 한계, 업데이트 절차가 구현과 일치한다.

AVF 특권 배포와 모든 선택적 고급 기능의 완성은 1.0의 필수 조건이 아니다.
다만 제공한다고 표시하는 기능의 검증 범위와 제한은 정확해야 한다.

## 개발 채널과 배포 절차

- 기존 표시 형식 `<base>+<main|dev>.<versionCode>.<source SHA 12자리>`를 유지한다.
  dev의 개발 배포 여부는 채널 및 GitHub prerelease 속성으로 구분한다.
  `+dev`를 SemVer의 `-dev` 사전 릴리스 우선순위로 해석하지 않는다.
- 설치 순서는 기본 버전 문자열이 아니라 기존 공유 `versionCode` 정책이 결정한다.
  기본 버전 승격을 위해 CI 순번·서명 키·앱 ID를 변경하지 않는다.
- 정식판 `TERM`(`dev.terminal.app`)과 프리릴리즈판 `TERM Preview`(`dev.terminal.app.prerelease`)는 별도 앱으로 설치한다. 공유 `versionCode` 순번은 유지하되 업데이트 순서는 각 패키지 안에서만 비교한다. 기본 버전의 사전 릴리즈 접미사는 dev 채널에서만 사용한다.
- 특별 목적 태그의 prerelease 접미사와 별도 서명 절차는 해당 산출물 문서를 따른다.
  이 정책 도입으로 과거 `v0.1.0-rootless.N` 태그를 변경하지 않는다.
- 승격 근거와 비교 범위, 검증 결과는 내부 출시 기록이나 작업 보고에 남긴다.
  사용자용 한국어 패치 노트에는 앱에서 추가·변경·삭제된 기능과 고쳐진 버그를
  중심으로 적는다. 필요한 업데이트 절차와 사용자에게 영향을 주는 호환성·제한은
  포함하되 빌드·CI·커밋 선별·구현 세부 사항은 노출하지 않는다.
  준비 노트는 `<base>.md`로 작성할 수 있다. 실제 게시 준비 시 확정된 버전 또는
  태그를 릴리스 ID로 사용하여 별도 노트를 만들고 출시일을 확정한다.
  준비일을 출시일로 주장하지 않는다.
- 버전 결정·커밋은 태그 생성, 푸시, 병합, 서명 배포 또는 게시의 승인이 아니다.
