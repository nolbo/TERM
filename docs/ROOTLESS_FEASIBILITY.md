# Rootless 파일 가속의 실현 가능성과 목표 조정

작성일: 2026-09-14. 실험 구현의 평가이며 제품 배포 승인이 아니다.

## 판단

최초 목표인 기본 Rootless 환경의 warm metadata 5배와 대표 작업 두 종류의
전체 시간 2배는 현재 구현으로 달성하지 못했다. 제한된 root-only dirfd
조회는 7.18배였지만 fake-root, bind, l2s를 사용하는 일반 실행에 적용되는
수치가 아니다. 불가능하다는 수학적 증명도 아니다. 현재 증거로 보장할 수
없는 수치를 이번 구현의 완료 조건으로 유지하지 않는다.

사용자의 실현 가능성 평가·목표 변경 지시에 따라 이번 목표를 다음으로 조정한다.

1. 실제 관찰한 중복 경로 조회·원격 문자열 읽기·실패 조회 재처리를 줄인다.
2. fake-root/bind/l2s를 사용하는 정의된 warm 작업 네 종류를 7쌍으로 비교하고,
   각 작업 중앙값에서 5% 초과 성능 저하가 없는지 확인한다.
3. Debian/Ubuntu의 파일 결과·오류·링크·FD 전달·취소 회귀 시험을 수행한다.
4. 큰 폭의 가속에 필요한 구조 변경과 미검증 조건을 구분해 기록한다.

이는 모든 Android와 모든 Linux 프로그램에 대한 성능·호환성 보장이 아니다.
제품 승격에는 아래 별도의 검증이 필요하다.

## 최종 작업 측정

[원본 측정값](../tools/rootless/faststat/results/open-path-2026-09-14.json).
ARM64 API 35 redroid의 Debian, app UID, ext4에서 mode 2와
`-0 --link2symlink` 및 기본 bind를 사용했다. 동일 실험 PRoot에서 DSO 가속과
open 최적화를 함께 켜고 끄며 순서를 교대했다. 입력 count는 1,000이다.

| 작업 | 끔 중앙값(ms) | 켬 중앙값(ms) | 시간 감소 |
| --- | ---: | ---: | ---: |
| 메타데이터 조회 | 65.857 | 50.129 | 23.88% |
| 파일 생성·변경·삭제 | 375.664 | 373.338 | 0.62% |
| Python import | 200.391 | 193.509 | 3.43% |
| tar 추출 | 904.534 | 896.644 | 0.87% |

네 중앙값 모두 5% 초과 회귀는 없었다. 1% 미만의 차이는 확실한 개선으로
해석하지 않는다. cold cache, 10만 파일, 동시 작업, Git/dpkg/build 전체를
검증한 결과가 아니다. guest CPU 시간은 tracer CPU를 포함하지 않으므로
전체 작업의 개선 불가능한 시간 하한으로 사용하지 않는다.

DSO 없는 raw openat/pread/close 3,000회는 open 최적화만 비교하여
170.642 → 164.287 ms(3.72% 감소)였다. 별도 카운터 실행에서는
read_string 9,339 → 3,119, 원격 메모리 읽기 9,517 → 3,289,
l2s readlink 3,119 → 11이었다. syscall enter/exit 수는 동일했다.

## 후보별 구현과 판단

| 후보 | 현재 결과 | 남는 비용 또는 필요한 다음 구조 |
| --- | --- | --- |
| 경로 해석 중복 제거 | 한 요청 내 디렉터리 재사용 구현 | 호출 간 변경을 감지하는 캐시는 별도 설계 필요 |
| 실패 조회 개선 | 프로토콜 4의 이번 요청 ENOENT 응답 구현 | 다른 오류·미지원 경로는 기존 처리 |
| 파일 열기 개선 | tracer가 방금 쓴 경로 재사용과 중복 readlink 제거 | 원래 커널 open과 tracer 진입은 유지 |
| glibc 내부·정적 프로그램 | core open 최적화는 DSO 없이 적용, 동적·정적 시험 통과 | 전체 stat/변경 연산의 직접 연결은 미구현 |
| 일반 환경의 tracer 진입 제거 | root-only 제한 모드에서만 구현 | cwd/bind/identity/FD 상태 공유, fork/exec/동시 변경 및 내부 syscall 연결 필요 |
| 실제 하드링크 저장 | 현 시험 환경 app UID의 native link/nlink=2 확인 | 기존 l2s 데이터 마이그레이션, 혼합 형식, 저장소·stock 정책 검증 필요 |

open을 preload wrapper로 바꾸지 않고 PRoot core를 개선했다. 원래 libc의
취소 지점과 커널 FD 생성을 유지하면서 raw syscall과 정적 ELF에도 중복
제거가 적용되기 때문이다. 이 구현을 open의 0-stop 가속으로 부르지 않는다.

## 큰 폭의 가속에 필요한 조건

tracer 진입을 남긴 미세 최적화만으로 전체 작업 2배를 약속할 근거가 없다.
전체 시간 중 개선 가능한 비중을 p, 그 부분의 가속을 s라 하면 전체 가속은
`1 / ((1-p) + p/s)`다. 적용률과 원래 병목을 함께 측정해야 한다.

후속 재설계는 읽기 전용·고정 경로 영역의 상태 공유부터 평가할 수 있다.
지원 프로그램이나 경로 변경을 제한하면 캐시와 직접 호출의 적용 범위가
넓어질 수 있지만, 일반 Debian 바이너리를 그대로 지원하는 조건과 다르다.
제한 모드는 명시적으로 선택해야 하며 기본 Rootless의 자동 대체가 아니다.
데이터 손실, 잘못된 파일 참조, 쓰기 성공의 허위 응답은 허용할 타협이 아니다.

native hardlink는 현재 ext4에서 가능하다는 증거만 있다. 기존 rootfs에 l2s를
끄는 방식은 마이그레이션이 아니며 링크 의미를 깨뜨릴 수 있으므로 채택하지
않았다. 새 rootfs 전용 backend와 혼합 읽기·복원 시험을 먼저 설계해야 한다.

## 검증 범위와 제품 승격 조건

Android MCP로 별도 실험 APK의 Debian/Ubuntu 실행을 검증했다. 동적·정적
open 시험은 flags, 오류, 링크, dup, fork/SCM_RIGHTS, libc 취소를 포함한다.
기존 stat C 시험과 Python 회귀 시험도 실행했다. 이 시험들이 모든 경합을
증명하지는 않는다. 앱 기본 payload와 사용자 세션은 교체하지 않는다.

시험 장치는 SELinux unconfined이며 일반 앱의 stock 보안 정책을 대표하지
않는다. stock 앱에서의 syscall/실행 정책, 큰 입력과 다중 작업, Git/dpkg/build,
전력·발열·장시간 안정성은 제품 승격 전에 남은 검증이다. 실제 hardlink와
일반 환경 0-stop dispatcher는 별도 구현 과제이며 완료했다고 주장하지 않는다.

이번 후속 변경은 새로운 외부 API를 도입하지 않아 로컬 소스를 근거로 했다.
UI 변경과 외부 앱 작업이 없어 replicant, context7, codex_apps 추가 호출은
필요하지 않았다. 빌드와 세부 회귀 결과는 [실험 기록](../tools/rootless/faststat/README.md)을 따른다.
