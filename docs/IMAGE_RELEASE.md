# Debian ARM64 image release procedure

End users do not build or repackage Debian images. Users request the signed-build catalog's approved release in AVF environment settings, or confirm installation when selecting an uninstalled AVF profile. An approved installation downloads, decompresses, verifies and installs the image. Images declaring APT initialization support additionally boot through :vmhost and refresh package indexes before reporting completion; an approved profile launch can reuse that startup and waits for its own session preparation. Deferred installation can be requested later in environment settings. Ordinary debug/release builds include the reviewed default catalog in `image/catalog-approved.properties`. The initial approved release was `avf-debian-920f34393b22d3e00806b251796684b4a2ad6f2a`. The current default, `avf-debian-20261011`, includes the versioned direct shared-directory and Android primary-storage mounters plus file-transfer and port-reporting guest services. It retains installation-time full APT index initialization, virtio DHCP, guest DNS, the corrected `droid` home and passwordless guest sudo; its [Korean release notes](release-notes/avf-debian-20261011.md) record installation requirements and limits. Existing installed images and data are not replaced or reconfigured. A normal APK cannot gain custom VM privileges through this installer. Builds without an approved default or an explicit candidate catalog retain an empty catalog.

New producer images remove stale APT package/source/translation indexes and partial/binary/package caches before the first smoke boot, preserving repository sources, signing keys, Release/InRelease metadata and installed dpkg state. `clean-avf-apt.sh` implements the image-finalization policy without depending on a particular APT `distclean` version and rejects symlinked cache paths. Both boot gates check the sealed lower layer is clean.

New producer manifests include the optional `aptInitializationVersion=1` field, covered by the catalog-pinned manifest hash. Online installation creates a separate pending APT initialization receipt only after full verification of an image declaring that version. Older manifests omit the field and retain file-only installation; unknown initialization versions are rejected. The installer requests `:vmhost` to boot the selected environment and call the host-only guest initializer. A successful full `apt-get update` with `Acquire::PDiffs=false` and `APT::Update::Error-Mode=any` records completion against the installed manifest; the writable overlay contains the new indexes, while immutable image hashes remain unchanged. Timeouts, cancellation and repository failures preserve the verified files and permit initialization-only retry. This needs an image containing `droid-apt-init.service` and the maintenance endpoint; old installed guests are not modified by an APK update, and older image releases cannot gain the new endpoint. Previously installed images and older releases such as `avf-debian-20261005` retain their previous installation behavior; the new default applies only to new installations.

## Automated producer

New manifests also declare `virtiofsVersion=1`. Factory configuration requires the matching `virtiofs` module/built-in support, guest `droid` UID 1000, the versioned shared-directory mounter and `term-shares.service` ordered before sessiond. The initrd includes virtiofs support. The two offline boots check module loading and installed service/configuration (`TERM_AVF_VIRTIOFS_CONFIG_OK`); they do not claim a live host export. `tests/image/test_virtiofs.py` exercises the real mount script with controlled commands, including full-table validation and failed-mount rollback. Actual bidirectional filesystem I/O and Android platform server teardown still require the privileged AVF acceptance sequence. Existing installed images and the catalog pin stay unchanged until an explicitly authorized image release.

The repository's `Build approved AVF Debian image` workflow automatically prepares a candidate when image, guest, or related verification files are pushed to `dev`; promoting only `image/catalog-approved.properties` does not rebuild an unchanged producer. It can also be dispatched on `dev` with an explicit immutable release ID. An ARM64 runner builds the guest binaries, downloads Google's official AVF Debian archive, rejects unsafe archive entries, installs the TERM services and CLI, creates the three disks, rebuilds the matching initrd and creates the manifest and pinned catalog. It records the upstream archive SHA-256 and repository commit in `provenance.json`. An optional reviewed source SHA-256 rejects upstream changes. Unsupported archive formats or missing overlay kernel support fail instead of producing an apparently usable image.

The dependent APK job receives the factory metadata, verifies its source commit and the manifest hash supplied by the producer job, and builds a debug APK containing that exact catalog. It checks the embedded catalog, AVF driver, and Rootless payload before uploading the candidate APK. This review APK reuses the canonical Android workflow's version-code sequence; it is not a separate app channel release. Candidate production alone does not publish image assets or make their URLs usable.

Filesystem parsing and guest configuration run in a libguestfs appliance inside an unprivileged container with no network or writable source checkout. The producer installs its dependencies in the container; it does not install host system packages. Production requires Docker, an ARM64 host (or configured ARM64 emulation), and at least 24 GiB of free space on the output filesystem plus sufficient Docker storage. The workflow runs two QEMU boots and checks that the overlay root starts, the guest binaries execute, the config disk mounts read-only, and a file written on the first boot survives the second. Each boot also switches to non-root `droid`, verifies passwordless sudo, updates APT lists from a temporary local repository, checks package dependencies and installs/removes a probe package. The test uses normal APT state paths but temporary source options; the guest's upstream sources are preserved and the scratch overlay is reset before release hashes are generated. This is an offline image boot/package gate, not privileged AVF/device/vsock or Internet/DNS validation.

The producer configures `/home/droid`, locks password login and installs the validated root-owned sudoers policy for guest administration. It requires sudo, APT and dpkg tools from the upstream base and fails if they are absent or unusable. The new session unit permits sudo by setting `NoNewPrivileges=no`, while continuing to run as `droid`. These changes apply to newly produced images; installing a new APK does not update an existing guest's service/account policy. Build and publish a reviewed image candidate and explicitly approve its catalog before ordinary new installations can receive this setup.

The appliance uses the direct backend with `LIBGUESTFS_BACKEND_SETTINGS=force_tcg`, so hosted ARM64 runners do not require KVM. Without this setting, libguestfs can detect host KVM support while the container has no KVM device and select an unusable host GIC configuration. Debug/trace output is enabled to report appliance failures. Guest build failures terminate the factory immediately.

The producer requires the guest's `systemd-networkd` and `systemd-resolved`, installs a DHCP rule matching the `virtio_net` driver, and enables both services. It replaces the build-container `/etc/resolv.conf` with the guest resolver's `/run/systemd/resolve/stub-resolv.conf` symlink after `virt-customize` has finished, so temporary appliance resolver handling cannot restore the old file into the sealed image. Both boots require `TERM_AVF_NETWORK_CONFIG_OK`, checking the final symlink, the virtio DHCP rule, installed binaries and each service's enablement.

The direct-kernel smoke VM explicitly disables QEMU's default NIC with `-nic none`. It requires no network access or network boot ROM; the container can retain its minimal QEMU package set. The network configuration gate does not exercise a live NIC, DHCP lease, DNS lookup or Internet download. Android TAP/tethering and an upstream `apt-get update -o APT::Update::Error-Mode=any` still need a supported AVF target. Newly generated images receive this policy; existing installations and the approved catalog are not changed by modifying the producer.

Google's current direct-boot rootfs does not contain `/boot/vmlinuz-*` or `/lib/modules`; its paired initrd contains the matching kernel modules without a userspace boot script. The producer preserves Google's kernel, restores that single module tree inside the isolated guest, verifies overlay support through its module metadata, and generates an initramfs-tools ramdisk with the overlay hook. It rejects absent or ambiguous module trees rather than substituting another kernel. The system image grows to at least 6 GiB inside the appliance to hold modules, the generated initrd, and TERM services; larger inputs are never truncated. The two-boot gate remains mandatory to establish that this kernel and ramdisk actually boot and retain overlay writes.

For local product development, the same pipeline is one command:

```sh
python3 image/scripts/build-avf-image.py \
  --release-id avf-debian-1 \
  --base-uri https://github.com/nolbo/TERM/releases/download/avf-debian-1/ \
  --output image/build/approved
```

Use an immutable release ID consistently in the URI and command. This is a producer command, not an end-user setup instruction. The producer refuses to overwrite an existing release directory. The six original files remain available for optional offline installation; the workflow uploads gzip-compressed boot/disk files, `manifest.properties`, `catalog.properties`, `provenance.json` and `SHA256SUMS` as its artifact. The writable `home.img` contains the persistent overlay state, including home files and package changes. The production APT initialization probe uses only an offline fixture; it verifies failed repository handling, a successful full refresh and idempotent retry, then removes its completion receipt. A real networked AVF installation must additionally verify DNS, strict upstream index refresh, cancellation/retry and sibling-session preservation. The initial filesystem is reset after the two-boot test, before checksums are generated.

## Publication and product build

An app release or prerelease deployment request authorizes any required image production, verification, publication and catalog promotion under [AGENTS.md](../AGENTS.md) and [RELEASING.md](RELEASING.md). Complete those steps and include the verified catalog in the released APK without requesting separate image approval. Producer-source changes alone do not deliver guest features, and existing installed environments remain preserved.

The workflow's `publish` option is false by default and is available only through manual dispatch. Publication waits for both image verification and the catalog-bearing APK build. It requires an immutable release ID, previously committed Korean notes at `docs/release-notes/<release-id>.md`, and the publishing job’s repository `GITHUB_TOKEN` with `Contents: write` in public `nolbo/TERM`. The source commit must belong to shared `dev` history and is recorded in the artifact provenance. For an authorized publication, the factory stages its verified files in an unpublished TERM release draft. The APK job downloads only the factory metadata from that draft and validates its source commit and producer-supplied manifest hash. After the APK gate passes, the publication job downloads and re-verifies the full draft assets, publishes those same bytes, and verifies anonymous public downloads before approving a catalog. This job handoff does not depend on Actions artifact storage; candidate-only runs retain their artifact-based handoff. Debug APK and approved-catalog Actions uploads are optional, and their storage quota failures do not skip or block the required publication checks. Duplicate image release IDs fail without overwriting existing assets. Source and image publication now share TERM; imported source history is preserved under the default `dev` branch. Release approval/versioning and patch-note policy remain governed by `AGENTS.md` and `VERSIONING.md`.

An already verified candidate can be promoted without rebuilding it: download that successful run's image artifact, check its recorded source commit against shared `dev`, verify that it includes all image changes required by the app release, verify the full directory against the producer job's manifest hash, and publish those exact bytes with committed Korean notes. Publication still requires authorization and a new immutable release ID; an app release or prerelease deployment request supplies that authorization for required supporting images. Perform the same credential-free public verification below before approving the default catalog. This preserves the reviewed image and its hashes instead of creating different filesystem bytes in another factory run.

Runtime downloads must be available without credentials. The unified source and release repository is public; the workflow retains the existing TERM release URLs. HTTPS redirects to the GitHub asset CDN are supported, including signed query strings; content remains pinned by the manifest and artifact SHA-256 values. Host all five `<artifact>.gz` files beside the uncompressed `manifest.properties` at the catalog's URI. Never host mutable `latest` contents under an approved manifest hash. An OEM may use its own immutable HTTPS directory, but the repository's publication verifier intentionally accepts only the TERM repository.

After uploading assets, the publication job downloads the public manifest and streams all five images without authentication. It enforces download/expansion limits and compares the manifest and decompressed artifact hashes before producing the `avf-approved-default-<release-id>` artifact. Missing or damaged public assets fail approval and preserve any existing default pin. The workflow does not push source changes or automatically promote a catalog into app releases.

After review, repeat the public-download verification against the producer artifact and atomically write the default pin:

```sh
python3 image/scripts/verify-avf-release.py \
  --directory image/build/approved --metadata-only \
  --expected-commit <producer-source-commit> \
  --expected-manifest-sha <producer-job-manifest-sha256> \
  --approve image/catalog-approved.properties
```

Commit that verified `image/catalog-approved.properties` on `dev`. Ordinary debug/release builds and the existing Android CI then embed it without extra build properties. Do not commit example hashes or a candidate whose assets have not been published. Source pushes and publication still require the authorization specified in `AGENTS.md`.

For an isolated candidate build, an explicit factory catalog overrides the reviewed default:

```sh
./gradlew :android-app:assembleDebug \
  -PavfImageCatalog=image/build/approved/catalog.properties
```

`image:processResources` validates and embeds the catalog in the APK's Java resources, protected by the APK/product signature. A subsequent build without the property restores the reviewed default, or an empty catalog if no default exists; an earlier override never leaks into later APKs. Users never enter an image URL or checksum. Both ordinary APK variants already package the driver and retain `TerminalApplication`; compatible platform APIs and actual Android permission grants are still required as described in `DEPLOYMENT.md`.

Before publishing a usable product, install its signed APK on an AVF-capable privileged target and run `tests/integration/acceptance.sh`. The source build, a QEMU smoke pass or a stock redroid instance does not establish actual AVF support.

The local image directory picker remains available by design. It is useful for
offline and development installations, but it performs the same manifest and
checksum validation before a VM can be started.

New manifests additionally declare optional `androidStorageVersion=1`, which requires `virtiofsVersion=1`. The producer installs `mount-android-storage.sh` and `term-android-storage.service` as another required sessiond prerequisite. Both offline boots require `TERM_AVF_ANDROID_STORAGE_CONFIG_OK` to establish installed configuration and the no-export boot path; this is not a live Android storage I/O pass. Legacy manifests without the new marker remain usable and receive no primary-storage export. Current installed images and the approved catalog are unchanged until an authorized release.
